### The deviation: **correct — approved**, but the stated rationale is over-specified

**Empirically confirmed the load-bearing test discriminates.** I ran the brief's *literal* Step 2 snippet against `test_middleware_clears_a_stale_inherited_role_when_request_carries_none`'s exact setup (scratchpad only, working tree untouched):

```
=&gt; brief snippet FAILS the load-bearing test (stale role leaked)
```

The committed implementation returns `'static_default'`. The report's claim #1 is true as stated.

**The contextvars mechanism claim is correct.** `contextvars.Context` is copied from whatever context is current *in the creating code at task-creation time*; it is not re-derived per logical request. The implementer's description of this is accurate.

**But the *specific scenario* they describe is not the live path**, and a reviewer restating it would be wrong in detail. On MCPg's actual streamable-HTTP/SSE path the dispatch task inherits **this request's ASGI context**, not a long-lived session task's:
- `jsonrpc_dispatcher.py:684-685` — `sender_ctx.run(self._tg.start_soon, fn, *args)`, with `sender_ctx = self._read_stream.last_context` (`:501-505`)
- `_context_streams.py:37` — `ContextSendStream.send` snapshots `contextvars.copy_context()` at send time, i.e. in the ASGI POST task
- both server transports use context streams (`streamable_http.py:158-160`, `sse.py:138`)

and for a role-less request that ASGI context has `current_role is None`, because both ASGI setters are header/claim-conditional (`http_runtime.py:240-244`, `:176-190`). On that path the brief's early-return would *not* leak.

**The real justification — which does hold, and which I verified:**
1. The SDK has explicit `None`-fallback branches that land on a **long-lived task's** context: `jsonrpc_dispatcher.py:686` (`self._tg.start_soon` from the read-loop task when `sender_ctx is None`) and `runner.py:657-659` (`_sender_context` → `contextvars.copy_context()` of the relay task when the stream isn't context-aware).
2. Those long-lived tasks *can* carry a stale role: `_TenantRoleMiddleware`/`_OIDCAuthMiddleware` hold `current_role` **set across `await self._app(...)`** (`http_runtime.py:190-194`, `:261-265`) — precisely the window in which a stateful session's serving/relay tasks are created. That is the pre-existing "session-frozen" bug the old code's own comment documented, relocated rather than removed.
3. So the unconditional set makes MCPg's tenancy **independent of SDK context-propagation internals**, and reproduces the deleted `_role_from_request`'s `has_request ⇒ authoritative` contract exactly.

**No new bug introduced.** The unconditional set can only clobber a value *this* middleware did not set (it always resets its own in `finally`). A repo-wide grep finds exactly two other `current_role.set` sites — `http_runtime.py:190` and `:261`, both pre-existing, both unchanged — and **both stash the role on `scope` before setting the ContextVar**, so a legitimate per-request role is always re-derived identically by the new middleware. Clobber-to-`None` falls through to `settings.default_role` — the configured static default, fail-closed, identical to the old mechanism. There is no "request-scoped-but-not-HTTP default" that the unconditional set could destroy. stdio (`ctx.request is None`) is genuinely untouched, preserving the ContextVar path that `test_resolve_role_prefers_contextvar_over_default` covers.
